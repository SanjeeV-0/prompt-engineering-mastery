# Token and Cost Optimization for LLM Systems

## 1. Overview

Token and cost optimization is the process of reducing the resources required to run an LLM application while maintaining acceptable quality, reliability, and latency.

In production systems, costs can come from input tokens, generated tokens, repeated model calls, retrieval operations, reranking, tool execution, and evaluation workflows.

Reducing prompt length is only one part of optimization. A shorter prompt that causes more retries, incorrect answers, or expensive downstream processing may cost more overall than a longer, more reliable prompt.

The objective is to optimize the complete workflow rather than a single token count.

## 2. Understand Token Consumption

Tokens are the units used by language models to represent input and output. A token may correspond to a whole word, part of a word, punctuation, or another text fragment.

Token counts depend on the tokenizer, language, formatting, and content. Character count and word count are therefore imperfect estimates of token usage.

A typical request may consume tokens through:

- System and developer instructions.
- User messages.
- Conversation history.
- Retrieved documents.
- Few-shot examples.
- Tool outputs.
- Generated responses.
- Intermediate model calls.

For multi-stage workflows, total consumption includes tokens used across all stages, not just the final answer.

### Input and output tokens

Input tokens are supplied to the model. Output tokens are generated by the model.

Their prices may differ, and some providers offer different rates for cached input tokens or other processing categories. Use the current pricing rules for the actual model and API configuration rather than assuming a universal rate.

## 3. Model the Total Cost

A simplified request-cost model is:

\[
C_{\text{request}} =
\frac{T_{\text{in}}P_{\text{in}}}{10^6}
+
\frac{T_{\text{out}}P_{\text{out}}}{10^6}
\]

where:

- \(T_{\text{in}}\) is the number of billable input tokens.
- \(T_{\text{out}}\) is the number of billable output tokens.
- \(P_{\text{in}}\) is the input price per million tokens.
- \(P_{\text{out}}\) is the output price per million tokens.

This formula is illustrative. Actual billing may distinguish cached tokens, reasoning tokens, model tiers, tool use, or other categories.

For a multi-stage workflow, total cost is approximately the sum of all billable operations:

\[
C_{\text{workflow}} =
\sum_{i=1}^{n} C_i
+
C_{\text{tools}}
+
C_{\text{infrastructure}}
\]

The complete cost model should include relevant non-model expenses, such as vector database usage, reranking, orchestration, storage, and monitoring.

### Example

Suppose a hypothetical model charges:

- $2 per million input tokens.
- $8 per million output tokens.

A request consumes 10,000 input tokens and 1,000 output tokens.

The estimated model cost is:

\[
\frac{10{,}000 \times 2}{1{,}000{,}000}
+
\frac{1{,}000 \times 8}{1{,}000{,}000}
= \$0.028
\]

These prices are illustrative, not current pricing for a specific provider.

At scale, even small per-request costs can become material. However, cost optimization should also account for answer quality and the cost of failures.

## 4. Measure Before Optimizing

Begin by collecting measurements from representative workloads.

Useful metrics include:

| Metric | Why it matters |
|---|---|
| Input tokens per request | Identifies context-heavy operations |
| Output tokens per request | Identifies overly verbose generation |
| Model calls per task | Reveals unnecessary pipeline stages |
| Cost per successful task | Connects spending to useful outcomes |
| Retry rate | Reveals instability and wasted inference |
| Cache hit rate | Measures reuse of eligible work |
| Latency | Captures responsiveness |
| Error rate | Detects quality or reliability regressions |
| Context truncation rate | Identifies requests that exceed intended limits |

Measure these by task type, model, and workflow stage where practical.

Average token usage can hide important outliers. Track distributions and high-percentile usage for workloads with large documents or variable-length outputs.

## 5. Optimize Input Tokens

Input tokens often accumulate through instructions, repeated history, examples, and retrieved material.

### Remove redundant instructions

Repeated statements rarely add value when they do not clarify a new requirement.

Consolidate overlapping rules while preserving critical constraints and failure behavior.

### Reduce irrelevant context

Include information needed for the current task instead of passing every available document or conversation turn.

Use targeted retrieval and context filtering where appropriate.

### Compress repeated state

Represent stable decisions and intermediate results in a compact, structured form when the task allows it.

Preserve important dates, values, exceptions, source identifiers, and unresolved questions.

### Optimize examples

Use examples that cover important behavior rather than adding many similar demonstrations.

Evaluate whether each example improves accuracy enough to justify its token cost.

### Avoid premature compression

A shorter context is not automatically better. Removing a qualification or source reference can increase hallucinations, retries, and downstream verification costs.

Measure both token savings and task performance.

## 6. Optimize Output Tokens

Generated tokens can be expensive and can increase latency.

Useful strategies include:

- Specify the required level of detail.
- Use concise output schemas for machine-consumed responses.
- Avoid requesting explanations that downstream applications do not use.
- Set appropriate output-token limits.
- Return only necessary fields when using structured extraction.
- Separate internal processing from user-facing presentation where appropriate.

Output limits must be chosen carefully. If the limit is too low, responses may be truncated or incomplete.

For example, an extraction task may need only:

```json id="n1u5de"
{
  "category": "billing",
  "priority": "high",
  "needs_review": true
}
```

A long narrative explanation would add cost if the application only needs these fields.

The correct output format depends on the downstream consumer. Human-facing explanations may require more detail than machine-to-machine interfaces.

## 7. Reduce Unnecessary Model Calls

Each additional model call adds cost, latency, and potential failure points.

Review the workflow for:

- Repeated summarization of unchanged content.
- Redundant validation calls.
- Unnecessary prompt-chaining stages.
- Duplicate retrieval or reranking.
- Repeated classification of the same input.
- Unbounded retries.
- Multiple candidate generations that provide little measurable benefit.

Do not remove a stage solely because it consumes tokens. A validation step may prevent costly errors, and a retrieval step may be necessary for factual accuracy.

The objective is to remove calls whose contribution is lower than their operational cost.

## 8. Model Routing

Not every task requires the same model.

A routing system can send simpler tasks to a lower-cost model and reserve more capable models for tasks that need stronger reasoning, longer context, or more complex instruction following.

Possible routing signals include:

- Task type.
- Input length.
- Required accuracy.
- Output complexity.
- Availability of deterministic validation.
- Confidence from a calibrated routing model.
- Failure history for similar requests.

A simple routing policy might send routine classification to one model and complex document synthesis to another.

However, routing adds its own complexity. A misrouted task can produce incorrect results, require escalation, or cost more through retries.

Evaluate routing against a baseline that uses one model for all requests. Measure end-to-end accuracy, escalation rate, latency, and cost per successful task.

## 9. Caching

Caching avoids repeating work when requests or intermediate results can safely be reused.

Common forms include:

### Exact-response caching

Store a result for an identical request under a defined configuration.

This works best when the output is stable and all relevant inputs can be included in the cache key.

### Retrieval caching

Cache search results for repeated queries when the underlying corpus and permissions have not changed.

### Embedding caching

Reuse embeddings for unchanged text when the embedding model and relevant preprocessing configuration are identical.

### Intermediate-result caching

Cache deterministic or validated intermediate stages in a multi-step workflow.

### Provider prompt caching

Some model APIs support discounted processing of eligible repeated input prefixes. Availability, pricing, cache rules, and minimum prefix requirements vary by provider.

Prompt caching is distinct from response caching: it can reduce repeated input-processing cost without necessarily eliminating generation.

### Cache invalidation

A cache can become incorrect if the source data, permissions, prompt, model configuration, or business rules change.

Cache keys and invalidation rules should account for every dependency that affects the result. Do not reuse private or permission-sensitive results across users unless the access model explicitly allows it.

## 10. Retrieval and Context Cost

Retrieval-augmented systems can spend significant tokens on source passages.

Ways to reduce this cost include:

- Improving query relevance.
- Removing duplicate passages.
- Filtering irrelevant results.
- Using reranking to prioritize stronger evidence.
- Retrieving parent sections only when additional context is necessary.
- Limiting evidence to the requirements of the question.
- Using structured extraction before final synthesis.

The number of retrieved passages should not be optimized in isolation. Too few passages can cause missing evidence, while too many can increase cost and distract the model.

Evaluate retrieval recall, grounded answer accuracy, and total token usage together.

For tasks requiring exhaustive coverage, do not reduce evidence solely to meet a token target. Use staged processing or hierarchical synthesis instead.

## 11. Multi-Stage and Agentic Workflows

A workflow that uses multiple agents, tools, or prompt chains may consume far more tokens than its final response suggests.

Potential sources of overhead include:

- Repeating the original task in each stage.
- Passing full histories between agents.
- Generating lengthy intermediate explanations.
- Re-running successful stages.
- Repeatedly asking evaluators to score similar outputs.
- Using multiple candidates without measurable benefit.

To optimize these workflows:

1. Define the minimum inputs each stage requires.
2. Pass validated state instead of full histories where appropriate.
3. Use explicit output contracts.
4. Store intermediate results that are safe to reuse.
5. Bound retries and candidate counts.
6. Measure the contribution of each stage.
7. Preserve validation that materially improves reliability.

A more expensive workflow may still be preferable if it significantly improves correctness or reduces costly downstream failures.

## 12. Latency Optimization

Cost and latency are related but not identical.

A workflow can consume many tokens but achieve acceptable latency through parallel execution. Conversely, a small workflow can be slow if it performs many sequential calls.

Latency depends on factors such as:

- Model processing time.
- Input and output length.
- Queueing and network delay.
- Number of sequential stages.
- Tool execution time.
- Retrieval and reranking.
- Retry behavior.

Possible improvements include:

- Running independent retrieval operations in parallel.
- Parallelizing independent candidate generation when justified.
- Removing unnecessary sequential dependencies.
- Streaming user-facing responses when appropriate.
- Reusing eligible cached results.
- Choosing a model suited to the task's latency requirements.

Parallel execution can increase peak resource use and does not necessarily reduce total token cost.

Measure end-to-end latency rather than assuming that fewer tokens always produce a proportionate speed improvement.

## 13. Quality-Adjusted Cost

The cheapest individual request is not necessarily the cheapest successful task.

Suppose one configuration costs less per attempt but fails frequently, requiring retries or human correction. Another configuration may cost more per attempt but complete the task correctly more often.

A useful metric is:

\[
C_{\text{success}} =
\frac{C_{\text{total}}}{N_{\text{successful tasks}}}
\]

where total cost includes all attempts and relevant processing costs during the evaluation period.

This metric should be interpreted alongside task quality. A system that achieves a low cost per successful task by silently abandoning difficult cases may still be unsuitable.

For safety-critical or high-impact tasks, define minimum quality and coverage requirements before comparing cost.

## 14. Common Failure Modes

### Over-compression

**Problem:** Important evidence or constraints are removed to reduce token usage.

**Correction:** Measure correctness alongside token savings and preserve task-critical details.

### Excessive output limits

**Problem:** Responses become truncated or omit required fields.

**Correction:** Set limits based on expected output distributions and validate completion.

### Too many retries

**Problem:** Failed tasks trigger repeated calls without a meaningful change in strategy.

**Correction:** Bound retries and use differentiated recovery paths.

### Over-aggressive model routing

**Problem:** Difficult requests are sent to models that cannot handle them reliably.

**Correction:** Evaluate routing decisions and define escalation conditions.

### Incorrect caching

**Problem:** Stale results or results from the wrong context are reused.

**Correction:** Include relevant dependencies in cache keys and implement invalidation policies.

### Removing validation

**Problem:** A small token saving increases downstream errors.

**Correction:** Keep validation that materially reduces risk and measure its return on cost.

### Optimizing average usage only

**Problem:** Large or unusual requests exceed budget despite acceptable average token counts.

**Correction:** Monitor high-percentile usage and define limits for outlier cases.

## 15. Practical Optimization Workflow

A repeatable process can be organized as follows.

### Step 1: Establish the baseline

Measure token usage, model calls, quality, latency, and cost on a representative workload.

### Step 2: Identify the largest cost contributors

Determine whether spending is dominated by input context, output length, retries, model selection, retrieval, or repeated calls.

### Step 3: Form an optimization hypothesis

For example, identify whether repeated history is redundant or whether retrieval returns excessive duplicate passages.

### Step 4: Make a controlled change

Change one major factor and preserve the baseline configuration for comparison.

### Step 5: Evaluate regressions

Measure correctness, constraint adherence, coverage, and robustness—not just cost.

### Step 6: Compare quality-adjusted cost

Calculate the resource cost of successful outcomes and check whether mandatory quality thresholds are maintained.

### Step 7: Deploy and monitor

Version the configuration, monitor real workloads, and retain a rollback path.

## 16. Production Checklist

Before deploying cost optimizations, verify that:

- [ ] Input and output token usage is measured.
- [ ] Costs are calculated using current provider pricing.
- [ ] Redundant instructions and context have been identified.
- [ ] Output length is appropriate for the consumer.
- [ ] Model-call counts and retries are bounded.
- [ ] Model routing is evaluated end to end.
- [ ] Cache keys and invalidation rules account for dependencies.
- [ ] Retrieval changes preserve required evidence coverage.
- [ ] Latency is measured across the complete workflow.
- [ ] Quality and safety constraints remain satisfied.
- [ ] Large-input and high-percentile workloads are tested.
- [ ] Cost per successful task is tracked.
- [ ] Changes are versioned and reversible.

## 17. Key Takeaways

Token and cost optimization requires measuring the full LLM workflow, not just shortening prompts.

The most reliable improvements often come from removing redundant context, controlling output size, reducing unnecessary calls, caching reusable work, and routing tasks appropriately.

The central principle is to minimize the cost of achieving a correct, complete, and acceptable result—not simply to minimize tokens per request.
